# Production EDSDK worker lifecycle

Apertrove confines EDSDK calls to a generation-scoped Electron utility process. The main process owns the worker RPC client, photo-transfer consumer, camera-session state, and the decision to retire or replace that process.

Each worker has a sticky SDK-initialization gate. A successful SDK session can serve repeated camera discovery, connection, and property requests in that same worker. If a candidate cannot be loaded before EdsInitializeSDK is attempted, the worker may continue through the configured compatible runtime candidates. Once it calls EdsInitializeSDK, whether that call succeeds, returns an error, or throws, it cannot initialize again or advance to another DLL. The gate is never reset during cleanup.

Runtime discovery and runtime selection use the process boundary. An explicit recheck or a changed SDK folder first retires the exact prior worker: stop admission, finish owned RPC work, fence transfers, account for that generation's photo messages, persist acknowledged imports, finalize and await process exit, then drain and persist once more. Late photo messages remain attached to their original generation and consumer. A new generation starts only after the existing strict shutdown coordinator reports CLOSED.

The Canon API reference establishes the process-level initialize/terminate lifecycle, while Apertrove cannot independently prove Canon's native quiescence after a native candidate-load attempt. The worker currently marks native work started before loading Windows or Canon libraries, so even a load failure before EdsInitializeSDK may conservatively report UNKNOWN_TERMINATION. Apertrove does not present that result as successful cleanup and does not start a replacement in the same application process. A later operation cannot silently retry. Restarting the application is an explicit new process boundary. Failures before a native candidate-load attempt, including synthetic-provider checks, can use the existing native-not-started proof. No proof is inferred from a zero exit code alone.

An unexpected worker exit, an unknown native result, an unacknowledged transfer, or an unknown retirement quarantines further worker creation for the lifetime of the main process. The application retains the diagnostic and registration evidence available from the old channel; it does not discard or relabel pending photo transfers as complete. Existing EOS discovery, multi-camera listing and selection, custom SDK folders, runtime candidate discovery, and camera capability reporting continue through the same provider and capability seams.

The user-facing runtime description remains: **Apertrove works with compatible Canon EDSDK runtime libraries installed separately by the user.** Canon binaries are not bundled. Picture Style Editor is one potential source of x64 Canon components, not an exclusive source; this change does not claim that every PSE release is compatible or settle the separate Canon use-rights question.

Lifecycle regressions are exercised with fake providers, in-memory RPC/transfer ports, synthetic clocks, and source-extracted functions. They do not load Koffi, Canon DLLs, or a camera and do not prove real Canon teardown. Real-device qualification remains separate.
